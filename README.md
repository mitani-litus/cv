# 履歴書データ化

**履歴書を、かんたんにデータ化。**

Webブラウザ上で履歴書の情報を入力し、**PDF・CSV・JSON**として出力できるオープンソースソフトウェアです。

採用管理システム（ATS）ではありません。

既存の採用管理システムや業務システムを置き換えるのではなく、これまでWordや紙などで扱われてきた履歴書を、**再利用可能な構造化データへ変換するためのシンプルなツール**を目指しています。

- 公開URL：https://cv.code4hachioji.org/
- 仕様書：[`docs/spec.md`](docs/spec.md)
- 設計メモ：[`docs/design.md`](docs/design.md)

> MVP（最小限の機能）の段階です。

## 🌱 このプロジェクトについて

日本では現在も、履歴書をWordやPDFなどのドキュメントとして提出・受領する場面が多くあります。

一方で、採用担当者がその内容を別のシステムへ転記したり、データとして再利用したりするには手間がかかります。

このプロジェクトでは、

> **「履歴書というドキュメントを、データとして扱えるようにする」**

ことを目的としています。

そして、もう一つ大切にしている考え方があります。

> **履歴書をデータ化するが、履歴書データを保有しない。**

## 🔒 データをクラウドに保存しません

このサービスでは、履歴書の入力データをクラウド上のデータベースやストレージに保存しません。

PDF・CSV・JSONの生成処理は、**利用者のWebブラウザ上で完結**します。公開サイト（GitHub Pages）では、入力内容をサーバーへ送信しません。

そのため、履歴書の内容をサービス提供者が継続的に保有する仕組みを持たず、利用者自身の端末に生成されたファイルを保存して利用できます。

この設計により、

* アカウント登録不要
* データベース不要
* 履歴書データの長期保存不要
* サービス提供者によるデータ削除依頼への対応負担を低減
* データバックアップによる意図しない長期保管を回避

といったシンプルな運用を目指しています。

具体的には、次のように扱います。

* 入力中のデータは、ブラウザのメモリの中だけに置きます。LocalStorage・Cookie・URL には保存しません。ページを閉じると消えるため、途中で中断するときは「入力データを保存（JSON）」でファイルに保存できます。
* 通信するのは、画面のファイルと、PDF用の日本語フォントを読み込むときだけです。
* 入力内容を広告に利用することはありません。広告は別のオリジンのページを sandbox 付きの iframe で表示し、入力画面には表示しません。
* サーバー（AWS Lambda）でPDFを作る構成（下記「デプロイ」）も用意しています。この構成では、PDFを作成するときだけ入力内容をサーバーへ送ります。サーバーではメモリ上でPDFを作って返し、保存しません。ログに個人情報は出力しません。

※ブラウザや利用者の端末側で行われる保存・キャッシュ等については、利用者の環境に依存します。

## ✨ 主な機能

**応募者向け**

* 履歴書情報のWeb入力（6つのステップ）
  * 基本情報（姓・名・ミドルネーム、生年月日、住所、連絡先など）
  * 学歴・職歴の複数登録（1校・1社ごとに、入学と卒業、入社と退職を入力）
  * 資格・免許の複数登録
  * 志望動機・自己PR・本人希望の入力
* 入力内容の確認
* 履歴書PDF・CSV・JSONの生成
* 入力途中のデータをJSONで保存し、後で続きから入力
* 写真をはる欄（空欄）・性別欄（記載は任意）を、必要に応じてPDFに設ける
* スマートフォン・PCに対応

**採用担当者向け**

* このサービスで作成したPDFを読み込み、CSV・JSONを作成（PDFだけが届いた場合）

作成したファイルは、応募者が自分で採用担当者に送ります。このサービスから送信することはありません。

## 📄 出力形式

### PDF

一般的な日本の履歴書として利用できる形式（A4・2ページ）のPDFを生成します。

印刷やメール等による提出を想定しています。

PDFには履歴書のJSONを添付しています。採用担当者は、このサービスでPDFを読み込むと、同じ内容のCSVを作成できます。

### CSV

履歴書の内容を表形式のデータとして出力します。

採用管理システム等へのデータ取り込みや、独自の業務システムでの利用を想定しています。

繰り返す項目は別のファイルに分け、3つのファイルを1つのZIPにまとめます。3つのファイルは、各ファイルの先頭列の「応募者ID」で紐づきます。

| ファイル | 単位 |
|---|---|
| `resume.csv` | 1行 = 1人（氏名・住所・連絡先・資格・志望動機など） |
| `education.csv` | 1行 = 1校（入学と卒業・修了を1行に） |
| `work.csv` | 1行 = 1社（入社と退職を1行に） |

BOM付きUTF-8で、Excelでもそのまま開けます。日付は ISO 8601（`2026-10-07`、年月は `2026-10`）、電話番号は E.164（`+81345007765`）にそろえます。列の詳細は [`docs/design.md`](docs/design.md) の「CSVの仕様」を参照してください。

### JSON

このプロジェクトでは、履歴書の構造化データをJSONとして扱います。

JSONを基本となるデータモデルとすることで、将来的に別の形式への変換や、他のシステムとの連携を行いやすくしています。

```text
履歴書JSON
   ├── PDF
   ├── CSV
   └── その他のデータ形式
```

## 🏛️ 履歴書の形式について

日本国内で一般的に利用されている履歴書の項目・帳票構成を参考にしています。

帳票設計については、JIS Z 8303を含む関連する帳票設計の考え方を参考にしていますが、特定の履歴書様式そのものを複製・再配布するものではありません。

また、本プロジェクトでは利用者のプライバシーや運用上のシンプルさを考慮し、顔写真の画像の登録・保存・PDFへの埋め込みには対応していません。写真が必要な場合は、PDFに空欄の「写真をはる欄」（縦40mm×横30mm）を設け、印刷した履歴書に写真をはって使います。

性別欄は任意です。設けるかどうかを選べ、設けた場合も空欄のままにできます。

## 🚫 このプロジェクトでは扱わないもの

本プロジェクトは、あえて機能を限定しています。

以下のような機能は、基本的に対象外です。

* 採用管理（ATS）
* 求人管理
* 応募者管理
* 面接管理
* 採用進捗管理
* 人事・給与管理
* 履歴書のクラウド保存
* ユーザーアカウント
* メッセージング
* AIによる志望動機・自己PRの自動生成

「何でもできる採用システム」ではなく、**履歴書をデータ化するという一つの問題をシンプルに解決すること**を重視しています。

## 🏗️ アーキテクチャ

本サービスは、可能な限りサーバー側の処理を必要としない構成を採用しています。

```text
┌─────────────────────┐
│      利用者          │
│                     │
│  履歴書情報を入力    │
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│     Web Browser     │
│                     │
│  ・入力              │
│  ・データ生成        │
│  ・PDF生成           │
│  ・CSV生成           │
│  ・JSON生成          │
└─────────┬───────────┘
          │
          ▼
       ダウンロード

        ※履歴書データを
        クラウドへ送信・保存しない
```

現在の公開サイトはGitHub Pagesでホスティングされています。

サーバーサイドのデータベースやオブジェクトストレージを必要としないため、非常に小さな運用負荷で公開・運用できます。

| 構成 | PDFを作る場所 | 用途 |
|---|---|---|
| **GitHub Pages（既定）** | ブラウザ | 静的ファイルだけで動く。サーバーは不要で、入力内容は端末の外に出ない |
| AWS（CloudFront + Lambda） | サーバー（Lambda） | サーバーでPDFを作る構成。下記「AWS へのデプロイ」 |

どちらの構成でも、CSV・JSONの作成とPDFの取り込みはブラウザの中で行います。

| パッケージ | 内容 |
|---|---|
| `packages/schema` | 履歴書JSONのスキーマと入力チェック（ブラウザとAPIで共用） |
| `packages/core` | CSV変換（3ファイル・ZIP）、表示用の整形、年齢計算（ブラウザで動作） |
| `packages/pdf` | 履歴書PDFの作成（PDFKit）。ブラウザと Lambda の両方で使う。履歴書JSONをPDFに添付する |
| `packages/web` | 入力フォーム、確認・完了画面、PDF取り込み画面（Vite + React） |
| `packages/api` | PDF生成API（AWS Lambda）。AWS 構成のときだけ使う |
| `infra` | AWS 構成のインフラ（AWS CDK） |

## 💻 ローカル開発

AWS に接続しなくても、入力フォームからPDF・CSV・JSONの作成、PDFの取り込みまで確認できます。

### 必要な環境

* Node.js 22 以上
* npm

### セットアップ

```bash
git clone https://github.com/mitani-litus/cv.git
cd cv
npm install
```

### 開発サーバー

```bash
npm run dev       # http://localhost:5173 。GitHub Pages と同じく、PDFもブラウザの中で作る
```

ブラウザから表示されたURLへアクセスしてください。

### テスト・ビルド

```bash
npm run check   # 型チェックとテスト
npm run build   # 本番用にビルド（packages/web/dist、packages/api/dist）
```

### Docker で動かす（AWS 構成の確認用）

PDFを Lambda で作る AWS 構成を、本番と同じ Lambda コンテナイメージで確認できます。

```bash
docker compose up --build
```

http://localhost:5173 を開きます。PDF生成APIは、本番と同じ Lambda コンテナイメージを AWS 公式の Runtime Interface Emulator で動かしています（読み取り専用のファイルシステムで起動）。

`public.ecr.aws` に接続できない環境では、Docker Hub にある同じイメージを使えます。

```bash
LAMBDA_BASE_IMAGE=amazon/aws-lambda-nodejs:22 docker compose up --build
```

Docker を使わずに AWS 構成を試す場合は、`npm run dev:api` を起動し、`VITE_PDF_API=/api/pdf` を設定して `npm run dev` を起動します。

## 🚀 デプロイ

### GitHub Pages

本プロジェクトは静的WebサイトとしてGitHub Pages等にデプロイできます。

GitHub Pagesを利用する場合、サーバーやデータベースを用意する必要はありません。

`main` に変更が入ると、GitHub Actions（`.github/workflows/pages.yml`）が画面をビルドして GitHub Pages に公開します。初回だけ、次の設定をします。

1. **Settings → Pages → Build and deployment → Source** を「GitHub Actions」にする
2. 独自ドメインを使う場合は、同じ画面の **Custom domain** にドメイン（例：`cv.code4hachioji.org`）を入力して保存し、DNS に CNAME レコードを追加する（例：`cv.code4hachioji.org` → `mitani-litus.github.io`）
3. DNS の確認が終わったら、**Enforce HTTPS** にチェックを入れる
4. **Actions → Deploy to GitHub Pages → Run workflow** で公開する（以後は `main` への push で自動的に公開される）

広告を表示する場合は、**Settings → Secrets and variables → Actions → Variables** に `CV_AD_URL`（広告ページのURL）を設定します。

注意：

* PDFを作るときに、日本語フォント（約3MB）を一度だけ読み込みます。
* GitHub Pages では HTTP ヘッダーを設定できないため、Content Security Policy は `<meta>` タグで設定しています。この方法では、ほかのサイトの画面への埋め込みを防ぐ設定（`frame-ancestors`）は使えません。

### AWS へのデプロイ

サーバー（Lambda）でPDFを作る構成です。GitHub Pages で公開する場合は不要です。

AWS CDK（`infra/`）で、次の構成を作成します。履歴書データを保存するデータベースやストレージは作りません。

```text
CloudFront（HTTPS、セキュリティヘッダー、CSP）
 ├─ /*      → S3（非公開。CloudFront からだけ読める。画面のファイルだけを置く）
 └─ /api/*  → API Gateway（HTTP API、スロットリング）→ Lambda（コンテナイメージ、ECR）
```

#### 必要なもの

* AWS アカウントと、デプロイできる権限を持つ認証情報（`aws configure` など）
* Docker（Lambda のコンテナイメージをビルドするため。Windows / macOS は Docker Desktop）
* Node.js 22 以上

#### 手順

```bash
npm ci
npm run cdk -w @cv/infra -- bootstrap   # 初回だけ（アカウントとリージョンごと）
npm run deploy                   # 画面（AWS 構成用）とAPIをビルドしてデプロイ
```

完了すると `SiteUrl`（CloudFront のURL）が表示されます。リージョンの既定は東京（`ap-northeast-1`）です。

#### 設定（任意）

`cdk deploy` に `-c 名前=値` で渡します（例：`npm run build:aws -w @cv/web && npm run build -w @cv/api && npm run cdk -w @cv/infra -- deploy -c domainName=cv.example.jp -c certificateArn=...`）。

| 名前 | 内容 |
|---|---|
| `domainName` / `certificateArn` | 独自ドメインと、us-east-1 の ACM 証明書。Lambda が受け付ける Origin にも加わる |
| `adOrigin` | 広告ページのオリジン（例：`https://ads.example.com`）。CSP の `frame-src` に加わる。画面側はビルド時に `VITE_AD_URL` も設定する |
| `throttleRate` / `throttleBurst` | API のスロットリング（既定：1秒あたり5件、瞬間的に10件） |
| `region` / `stackName` | リージョン（既定 `ap-northeast-1`）とスタック名（既定 `CvStack`） |

#### データが残らないことの確認

* **データベース**：作成しません（`infra/test` のテストで確認しています）。
* **S3**：画面のファイルだけを置きます。PDF・CSV・JSON は置きません。
* **Lambda**：PDF はメモリ上で作り、`/tmp` を含めてファイルに書きません（ローカルでは読み取り専用のファイルシステムで動作を確認しています）。
* **ログ**：Lambda のログは決められた項目（イベント名、リクエストID、ステータス、処理時間）だけです。API Gateway のアクセスログには、本文や送信元IPを記録しません。CloudFront のアクセスログは無効です。ログの保存期間は1か月です。
* デプロイ後は、PDF を1件作ってから、CloudWatch Logs に氏名やメールアドレスが含まれていないことを確認してください（例：Logs Insights で `filter @message like /@/`）。

## 🔐 セキュリティ

履歴書には氏名、住所、電話番号、メールアドレス、学歴、職歴などの個人情報が含まれる可能性があります。

そのため、本プロジェクトでは以下を重視しています。

* 履歴書データを永続保存しない
* 不要なサーバーサイド処理を行わない
* 個人情報をログへ出力しない
* 外部サービスへ不要な個人情報を送信しない
* CSV出力時のインジェクション対策
* 入力値の適切なバリデーション
* XSS等のWebセキュリティ対策

主な対策は次のとおりです。

* 通信はすべて HTTPS です（GitHub Pages の「Enforce HTTPS」、AWS 構成では CloudFront のリダイレクトと HSTS）。
* Content Security Policy で、読み込めるスクリプトや通信先を自分のサイトだけに限っています（GitHub Pages では `<meta>` タグ、AWS 構成ではヘッダー）。AWS 構成では、ほかのサイトの画面に埋め込むこともできません。
* 入力チェックは、ブラウザと API の両方で同じ規則で行います。想定外の項目（画像データなど）は拒否します。エラーの文に入力値は含めません。
* CSV では、Excel などで数式として扱われないよう、先頭が `=` `+` `-` `@` などの値を無害化します（CSV Injection 対策）。
* AWS 構成の PDF 生成 API は、自分のサイトからの呼び出し（`Origin` を照合）だけを受け付け、CORS は設定していません。大量の呼び出しは、API Gateway のスロットリングで抑えます。Lambda の権限は、ログの書き込みだけです。

既知の課題は [`docs/design.md`](docs/design.md) の「13. 残っている課題」にまとめています。
