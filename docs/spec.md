# 履歴書データ変換OSS システム仕様書

Version 0.1 / MVP

> 実装前に合意した変更点は [`docs/design.md`](design.md) にまとめています。食い違う場合は design.md を優先します。

## 1. プロジェクト概要

### 1.1 目的

日本国内で一般的に利用されているWord/PDF形式の履歴書について、採用担当者が行っている手作業による転記・データ化を削減する。

応募者がWebフォームから履歴書情報を入力すると、以下を自動生成する。

- 履歴書形式のPDF
- CSVデータ
- 構造化された履歴書JSON

本システムは採用管理システム（ATS）ではなく、履歴書情報の入力・変換・出力に特化した軽量なOSSとする。

### 1.2 基本コンセプト

履歴書をデータ化するが、履歴書データを保有しない。

入力された個人情報は原則としてクラウド上に永続保存しない。

必要な処理のために一時的にサーバー上へ渡す場合があるが、処理完了後は速やかに揮発させる。

### 1.3 想定利用者

**応募者**
採用担当者からURLを受け取り、履歴書情報を入力する。

**採用担当者**
応募者に入力URLを送付し、生成された履歴書PDF/CSVを取得する。

### 1.4 対象外

以下は本MVPでは実装しない。

- 求人管理
- 応募者管理
- 面接管理
- 採用進捗管理
- 人事評価
- 給与管理
- 勤怠管理
- 社員管理
- 顔写真の登録・保存・出力
- メールによる履歴書送信
- ユーザーアカウント管理
- 採用担当者向けDB
- 履歴書データの長期保存
- AIによる志望動機・自己PRの自動生成

## 2. 設計原則

### 2.1 Privacy by Design

個人情報を「安全に保存する」のではなく、可能な限り保存しない。

システム設計上、履歴書データを永続保存する機能を持たせない。

### 2.2 Stateless

APIは原則としてステートレスにする。

リクエスト単位で、

```text
入力
 ↓
検証
 ↓
JSON生成
 ↓
PDF/CSV生成
 ↓
レスポンス
 ↓
終了
```

という処理を基本とする。

### 2.3 DBレスを基本とする

MVPではRDB/DynamoDB等の永続データベースを使用しない。

履歴書データ保存のためのDBテーブルを作成してはならない。

### 2.4 顔写真を扱わない

顔写真は本システムの対象外とする。

- アップロードUIを設けない
- S3等への保存を行わない
- PDFへの写真埋め込みを行わない
- APIで画像データを受け付けない

## 3. 履歴書フォーマット

### 3.1 基準

履歴書の項目・帳票設計については、JIS Z 8303を基本的な参考基準とする。

ただし、現在のJIS Z 8303そのものが特定の履歴書様式を規定している、または特定項目を必須としているとは解釈しない。

特に性別欄などについて、JIS準拠を理由として必須化しない。

### 3.2 基本項目

**基本情報**

- 氏名
- 氏名フリガナ
- 生年月日
- 年齢
- 郵便番号
- 都道府県
- 市区町村
- 町名・番地
- 建物名
- 電話番号
- メールアドレス

**学歴**

複数行を登録可能とする。各行：

- 年
- 月
- 区分（入学・卒業等）
- 学校名
- 学部・学科
- 備考

**職歴**

複数行を登録可能とする。各行：

- 年
- 月
- 区分（入社・退職等）
- 会社名
- 部署・役職
- 備考

**資格・免許**

複数行を登録可能とする。各行：

- 年
- 月
- 資格・免許名
- 備考

**志望動機**：自由入力テキスト。

**自己PR**：自由入力テキスト。

**本人希望欄**：自由入力テキスト。

## 4. 内部データモデル

内部的な標準データ形式としてJSONを使用する。

例：

```json
{
  "version": "1.0",
  "personal": {
    "name": "",
    "nameKana": "",
    "birthDate": "",
    "age": null,
    "postalCode": "",
    "address": {
      "prefecture": "",
      "city": "",
      "street": "",
      "building": ""
    },
    "phone": "",
    "email": ""
  },
  "education": [
    {
      "year": null,
      "month": null,
      "category": "",
      "school": "",
      "department": "",
      "note": ""
    }
  ],
  "employment": [
    {
      "year": null,
      "month": null,
      "category": "",
      "company": "",
      "department": "",
      "position": "",
      "note": ""
    }
  ],
  "qualifications": [
    {
      "year": null,
      "month": null,
      "name": "",
      "note": ""
    }
  ],
  "motivation": "",
  "selfIntroduction": "",
  "preferences": ""
}
```

### 4.1 JSONを中心にする理由

CSVやPDFを内部データモデルにしてはならない。

JSONを正規の内部データモデルとし、

```text
              履歴書JSON
              /   |   \
             /    |    \
          PDF    CSV   API
```

という構造にする。

これにより、将来的な他システム連携やフォーマット追加を容易にする。

## 5. Webフォーム

### 5.1 入力画面

応募者はWebブラウザから履歴書情報を入力する。

画面構成：

1. 基本情報
2. 学歴
3. 職歴
4. 資格・免許
5. 志望動機
6. 自己PR
7. 本人希望
8. 入力内容確認
9. 生成・ダウンロード

### 5.2 動的行追加

学歴・職歴・資格は「追加」ボタンによって入力行を増やせるようにする。

例：

```text
学歴

[2015] [04] [入学] [○○高等学校]

[2018] [03] [卒業] [○○高等学校]

[＋ 学歴を追加]
```

### 5.3 ブラウザ内保持

入力途中のデータは、可能な限りブラウザ内で保持する。

サーバーへの自動保存機能は実装しない。

ブラウザのLocalStorage等を利用する場合は、明示的な「入力データを保存する」操作なしに永続保存しない。

## 6. 入力チェック

最低限以下を実装する。

**必須チェック**

- 氏名
- 氏名フリガナ
- メールアドレス
- 電話番号

その他の項目は原則任意とする。

**形式チェック**

- メールアドレス
- 電話番号
- 郵便番号
- 日付
- 年月

**セキュリティ上の入力チェック**

以下を適切にエスケープ・サニタイズする。

- HTML
- JavaScript
- CSV
- PDF

特にCSVでは、Excel等によるCSV Injectionを防止する。

## 7. PDF生成

### 7.1 目的

人間が履歴書として閲覧・印刷できるPDFを生成する。

### 7.2 方針

一般的な日本の履歴書様式を参考とした帳票とする。

ただし、特定企業・特定サービスの履歴書テンプレートをコピーしない。

### 7.3 顔写真

顔写真欄は設けない。

### 7.4 PDF生成方式

PDF生成処理はサーバーサイドで実施する。

Dockerコンテナ上で実行可能なPDF生成ライブラリを使用する。

日本語フォントを正しく埋め込めることを必須条件とする。

## 8. CSV生成

履歴書JSONからCSVを生成する。

基本的には1応募者＝1行とする。

例：

```csv
氏名,氏名フリガナ,生年月日,郵便番号,住所,電話番号,メールアドレス,志望動機,自己PR,本人希望
山田太郎,ヤマダタロウ,1985-04-01,100-0001,東京都...,090-...,example@example.com,...,...,...
```

学歴・職歴・資格については、以下のいずれかを採用する。

**MVP案**

列を固定数作る。

例：

```text
学歴1
学歴2
学歴3
職歴1
職歴2
職歴3
資格1
資格2
資格3
```

将来的には別CSVへの分離も検討する。

## 9. データ保存ポリシー

### 9.1 原則

履歴書情報を永続保存しない。

以下のデータベースを使用して履歴書情報を保存してはならない。

- RDS
- DynamoDB
- Aurora
- Firebase等の外部DB
- その他永続ストレージ

### 9.2 一時保存

PDF生成等のため、一時ファイルが必要になる場合は許容する。

ただし、

- 最小限の保存
- 最短時間
- 自動削除

を必須とする。

目標として、生成処理終了後速やかに削除する。

### 9.3 ログ

個人情報をログに出力してはならない。

禁止例：

```text
INFO name=山田太郎 email=test@example.com
```

許可例：

```text
INFO request_id=xxxx pdf_generation_completed
```

### 9.4 エラーログ

エラー内容に履歴書データが含まれないようにする。

## 10. アーキテクチャ

MVPではAWS Serverless Architectureを採用する。

基本構成：

```text
                       Internet
                           │
                       CloudFront
                           │
                    ┌──────┴──────┐
                    │             │
                    ▼             ▼
                  S3静的サイト   API Gateway
                                  │
                                  ▼
                              AWS Lambda
                            Docker Image
                              │       │
                              ▼       ▼
                          PDF生成    CSV生成
```

AWSサービス

- Amazon S3
- Amazon CloudFront
- Amazon API Gateway
- AWS Lambda
- Amazon ECR

原則としてDBは使用しない。

### 10.1 Lambda

PDF生成など依存ライブラリが多い処理については、Lambda Container Imageを利用する。

Lambdaはステートレスに設計する。

### 10.2 ECR

Lambda Container ImageをAmazon ECRで管理する。

## 11. セキュリティ

### 11.1 HTTPS

すべての通信をHTTPSとする。

HTTPアクセスはHTTPSへリダイレクトする。

### 11.2 CORS

API GatewayのCORSを適切に設定する。

不必要に、

```text
Access-Control-Allow-Origin: *
```

を使用しない。

### 11.3 IAM

AWS IAMは最小権限とする。

Lambdaに不要なS3/DynamoDB等の権限を付与しない。

### 11.4 個人情報の非保存

システム設計・コードレビュー・テストにおいて、個人情報が永続化される経路が存在しないことを確認する。

## 12. URL設計

MVPではユーザーアカウントを作らない。

採用担当者が応募者にフォームURLを共有する方式を想定する。

例：

```text
https://example.jp/form
```

必要に応じて将来的にフォーム単位の識別子を導入する。

例：

```text
https://example.jp/form/xxxxxxxx
```

ただし、URL自体に個人情報を含めない。

## 13. 出力方式

フォーム送信後、

```text
入力
 ↓
確認
 ↓
生成
 ↓
┌─────────────────┐
│ 完了             │
│                 │
│ [履歴書PDF]      │
│ [CSV]            │
│ [JSON]           │
└─────────────────┘
```

とする。

MVPでは、生成したファイルをブラウザへ直接返す方式を優先する。

S3等へファイルを保存してダウンロードURLを発行する方式は、必要性が確認された場合のみ採用する。

## 14. JSON出力

応募者本人が入力データを再利用できるよう、JSONダウンロードを提供する。

これはOSSとしての重要な設計思想とする。

```text
履歴書入力
    ↓
履歴書JSON
    ├── PDF
    ├── CSV
    └── JSON
```

特定サービスへのデータロックインを作らない。

## 15. AI機能

MVPではAI機能を必須としない。

ただし将来拡張として、以下を想定する。

**履歴書ファイル取り込み**

```text
Word
PDF
Excel
画像
  ↓
OCR / AI
  ↓
履歴書JSON
  ↓
本人確認

```

この機能を実装する場合も、AI提供者へ個人情報を送信することについて明示的な同意を取得する必要があるため、MVPでは実装しない。

**AIによる文章生成**

以下はMVPでは実装しない。

- 志望動機生成

- 職歴要約
- AIによる採用評価
- AIによる合否判定

本プロジェクトは「履歴書データの変換」に集中する。

## 20. 非機能要件

**可用性**
小規模利用を前提とし、AWS Serverless Architectureによって自動スケール可能な構成とする。

**性能**
通常の履歴書1件について、入力完了からPDF/CSV生成完了まで数秒以内を目標とする。

**コスト**
利用者が少ない場合に固定費を極小化する。ECS/Fargate、EC2等の常時稼働サーバーは原則使用しない。

**拡張性**
将来的に以下を追加できる設計とする。

- Word/PDF履歴書インポート
- AI/OCR
- 人事システムへのAPI連携
- 複数履歴書フォーマット
- 英語履歴書
- 他国フォーマット
- 採用管理システムとの連携

ただしMVPでは実装しない。

## 22. 開発AIへの実装指示

本仕様書に基づいて実装する場合、以下の原則を厳守する。

1. MVPに記載されていない機能を勝手に追加しない。
2. 個人情報を永続保存する仕組みを追加しない。
3. DBを追加しない。
4. 顔写真機能を追加しない。
5. 認証機能を追加しない。
6. 採用管理機能を追加しない。
7. AIによる文章生成機能を追加しない。
8. 外部AI APIへ履歴書情報を送信しない。
9. ログに個人情報を出力しない。
10. セキュリティを優先し、便利さのために個人情報を保存する設計を採用しない。
11. AWSの特定サービスへの依存を必要以上に増やさない。
12. OSSとして第三者がローカル環境で動作確認できるコードを維持する。
13. 実装上の判断に迷った場合は「データを保存しない」「機能を増やさない」方向を優先する。
14. 実装開始前に、リポジトリ構成、使用技術、AWS構成、データフローを提示し、仕様との矛盾がないことを確認する。

## 23. 将来構想

本プロジェクトは最終的に、単なる履歴書作成サービスではなく、

**履歴書という旧来のドキュメントを、オープンで再利用可能な構造化データへ変換するためのOSS**

を目指す。

ただし、MVPでは機能を増やさず、

「入力 → JSON → CSV/PDF → データ揮発」

という基本機能の完成度を優先する。

## 24. ワイヤーフレーム・UIデザイン指示

### 24.1 デザインの目的

本サービスは、応募者が採用担当者から送られてきたURLを開き、履歴書情報を入力してPDF/CSVを生成するサービスである。

利用者はITサービスに詳しいとは限らない。そのため、

- 初めてでも迷わない
- 入力項目が分かりやすい
- 現在どこまで入力したか分かる
- 入力ミスに気付きやすい
- スマートフォンでも使いやすい
- 公共サービスのような安心感がある
- しかし行政システムのように古臭く見えない

ことを最優先とする。

### 24.2 デザインの基本方針

デザインの基本的な考え方について、デジタル庁デザインシステムβ版（<https://design.digital.go.jp/dads/>）を参照する。

特に以下を参考にする：カラー、タイポグラフィ、フォーム、ボタン、ステップ表示、エラー表示、アクセシビリティ、フォーカス表示、レスポンシブ設計。

デジタル庁デザインシステムはアクセシビリティを最優先事項として設計されているため、本サービスも同様の思想を採用する。

ただし、デジタル庁のWebサイトをそのまま模倣するのではなく、本サービス独自のスタイリッシュなUIとして再構成する。

### 24.3 カラーテーマ

青をメインカラーとする（信頼感・公共性・清潔感・デジタル・安心感）。ただし、画面全体を青一色にしない。

```text
Primary       深めの青
Primary Light 薄い青
Background    ごく薄いグレーまたは白
Surface       白
Text          濃いグレー
Secondary     中間グレー
Success       緑
Warning       黄系
Error         赤系
```

青はCTA、リンク、ステップ表示など重要な箇所に集中して使用し、装飾目的で大量に使用しない。

テキストは原則4.5:1以上のコントラスト比を確保する。

### 24.4 全体のビジュアルイメージ

目指す方向：「行政サービス × モダンSaaS」

- デジタル庁らしい信頼感
- StripeやLinearのような整理されたUI
- 日本の公共サービスとしての分かりやすさ
- 過度な装飾を避けたミニマルデザイン

避けるもの：派手なグラデーション、過剰なシャドウ、ガラスモーフィズム、大量のイラスト、キャラクター、過剰なアニメーション、丸すぎるUI、スマートフォンアプリのような過度にカジュアルなUI、古い行政システムのような密集したフォーム。

### 24.5 レイアウト

PCでは最大幅1200px程度のコンテンツ領域を使用する。フォーム入力画面では、入力領域をさらに狭くして読みやすさを確保する。入力フォームは中央配置を基本とする。

### 24.6 ヘッダー

非常にシンプルなヘッダーとする（サービス名、「使い方」「このサービスについて」）。ロゴは文字ベースでもよい。サービス名は仮称「履歴書データ化」とし、後から変更可能な構造とする。

### 24.7 トップページ

- メインコピー（仮）：履歴書を、かんたんにデータ化。
- サブコピー：入力した履歴書から、PDFとCSVを作成できます。入力した情報は原則として保存されません。
- CTA：「履歴書を入力する」
- 特徴表示は3つ程度（かんたん／Webで入力、すぐ使える／PDF・CSV出力、安心／原則データ保存なし）

### 24.8 入力フォーム

1ページにすべての項目を詰め込まず、ステップ方式（基本情報 → 学歴 → 職歴 → 資格・免許 → 志望動機・自己PR → 確認 → 完成）を採用する。画面上部にステップインジケーターを表示し、現在位置を明確にする。

### 24.9 基本情報画面

- タイトル：基本情報
- 説明：履歴書に記載する基本的な情報を入力してください。
- 項目：氏名、フリガナ、生年月日、郵便番号、住所、電話番号、メールアドレス
- ラベルは入力欄の上に配置し、プレースホルダーだけをラベルとして使用しない。必須項目には明確に「必須」を表示する。

### 24.10 学歴画面

- タイトル：学歴
- 説明：高校以降の学歴を入力してください。
- 複数行入力でき、行を追加するとカード形式で表示する。削除ボタンは明確に表示する。

### 24.11 職歴画面

学歴と同じUIパターンを使用する（年・月・区分、会社名、部署・役職）。

### 24.12 資格・免許画面

取得年月、資格・免許名、「＋ 資格・免許を追加」。

### 24.13 志望動機・自己PR画面

大きなテキストエリアを使用する。文字数制限がある場合は、入力欄付近に表示する。

### 24.14 確認画面

入力内容を履歴書に近い見た目で確認でき、セクションごとに［編集］できる。下部に［戻る］［履歴書を作成］。

### 24.15 完了画面

入力完了後は安心感を与える。「履歴書を作成しました」、PDF・CSVのダウンロード、JSONのダウンロード、「このサービスでは、履歴書情報を原則として保存していません。」。「完了！」などのカジュアルな表現より、信頼感のある表現を使用する。

### 24.16 データ非保存の説明

推奨：入力した履歴書情報は、原則として保存されません。

補足：PDFやCSVの作成に必要な処理を行った後、入力データは保持しない設計になっています。

「絶対に保存されません」といった過度な断定表現は避ける。

### 24.17 ボタンデザイン

主要CTA（履歴書を入力する、次へ、履歴書を作成）は青色。副次的操作（戻る、編集、キャンセル）はアウトラインまたはテキストボタンとし、視覚的優先順位を明確にする。

### 24.18 エラー表示

入力エラーは赤枠だけでなく、具体的な説明を表示する（例：「メールアドレスの形式で入力してください。」）。色だけでエラーを表現せず、アイコンやテキストを併用する。

### 24.19 レスポンシブ

スマートフォンでの利用を最重要視する。

- スマートフォン：1カラム、大きめの入力欄、十分な大きさのボタン、横スクロールなし、ステップ表示は簡略化可能、固定フッターに「次へ」を配置する案も検討
- PC：中央配置、入力フォームの最大幅を制限、余白を十分に確保、情報密度を下げる

### 24.20 アクセシビリティ

JIS X 8341-3:2016 / WCAG 2.2 AA相当を目指す。キーボード操作、明確なフォーカス表示、十分なコントラスト、フォームラベル、エラーメッセージ、スクリーンリーダー対応、タップ領域、色だけに依存しない情報伝達を重視する。

### 24.21 アイコン

アイコンは補助的に使用し、アウトライン系のシンプルなものとする。アイコンだけで意味を伝えず、アイコン＋テキストとする。

### 24.22 装飾

装飾は最小限とし、大きめの余白、明確なタイポグラフィ、薄い境界線、subtleなカード、青を使ったアクセント、控えめな背景パターン、セクション間の明確な階層でスタイリッシュにする。

### 24.23 ワイヤーフレームの必須画面

1. ランディングページ
2. 基本情報入力
3. 学歴入力
4. 職歴入力
5. 資格・免許入力
6. 志望動機・自己PR入力
7. 入力内容確認
8. 完了画面
9. エラー状態
10. スマートフォン版

hover/focus/disabled状態も考慮する。目指すデザインイメージは「デジタル庁 × 現代的SaaS」。

### 24.24 ワイヤーフレームで特に確認すること

- 情報設計：何をするサービスか分かるか、「履歴書を入力する」まで迷わないか、現在のステップと次にすることが分かるか
- 入力：項目が多すぎると感じないか、学歴・職歴の追加方法が分かるか、エラーを修正しやすいか、スマートフォンで入力しやすいか
- 安心感：個人情報を保存しない設計であることが理解できるか、「送信したらどこかに登録されるのでは」という不安を感じさせないか
- 完了：PDFとCSVの取得方法が一目で分かるか、入力が完了したことが分かるか、ブラウザを閉じても大丈夫か等の説明が足りているか

### 24.25 デザイン上の最終方針

「履歴書を作るために使っている」という感覚をできるだけ減らし、「必要な情報を順番に入力するだけ」という感覚を作る。

キーワード：Simple / Trustworthy / Modern / Accessible
